# GuardianAI — Day 3 Runbook (Build Phase 3): Closing the Agentic Loop

**Goal of Day 3:** Turn insight into action. The **Remediation Agent** proposes
fixes (with confidence + risk + a human-approval gate); approved fixes execute
safely; the **Validation Agent** re-checks and proves the score jump.

**Full loop now complete:** Detect → Explain → Impact → **Recommend → Approve →
Execute → Validate**.

## Run order

| Step | File | What it does |
|------|------|--------------|
| 1 | `sql/11_create_remediation_table.sql` | Creates plan, quarantine, and history tables |
| 2 | `sql/12_remediation_agent.sql` | **Remediation Agent** → builds fix plan (SQL + confidence + risk + approval flag; AI narrates the recommendation) |
| 3 | `sql/13_apply_approved_fixes.sql` | Snapshots BEFORE, applies approval, **executes only APPROVED fixes** in safe order |
| 4 | `sql/14_validation_agent.sql` | **Validation Agent** → re-runs checks, recomputes score, shows BEFORE vs AFTER |

## The three fix strategies (say these in your demo)
- **AUTO_FIX** (in-place value repair): negative price/amount → absolute value,
  missing state → 'UNKNOWN', missing category → 'UNCATEGORIZED', invalid flag → 'N',
  future date / bad phone → nulled for review.
- **DEDUP**: keep one row per key for duplicate customer/order/product IDs.
- **QUARANTINE** (highest risk, always needs approval): missing keys, orphan orders,
  missing/invalid emails → moved to a quarantine table, never deleted.

## Why this wins points
- **Agentic AI (35%)** — the loop is now autonomous end to end, with the agent
  recommending and validating its own work.
- **Responsible AI (15%)** — human-approval gate + quarantine-not-delete +
  deterministic (auditable) fix SQL. AI advises; SQL executes; a human approves.
- **Business value (25%)** — a single, undeniable number: 43 → 100.

## Safe-execution design notes
- Fixes run in order **CUSTOMERS → ORDERS → PRODUCTS**, and within a table
  **QUARANTINE → DEDUP → AUTO_FIX**, so orphan detection runs against the
  *cleaned* customer set (no cascading orphans).
- `FIX_SQL` is deterministic and stored in the plan — fully auditable, never
  AI-generated at execution time.
- `RUN_APPROVED_FIXES()` only touches rows where `APPROVAL_STATUS='APPROVED'`.
